# Java Vibe Coding 工作流

## 概述
结合Vibe Coding原则与工程严谨性的结构化6阶段Java开发工作流。通过在整个项目生命周期中强制执行“先规划，后编码”的纪律，确保代码可维护、可测试。

## 何时使用

- 使用AI辅助启动新的Java/Spring Boot项目时
- 向现有Java项目添加主要功能时  
- 当AI生成的代码变得不一致或难以维护时
- 在时间压力下需要交付高质量结果时
- 当多个开发人员需要协作AI辅助代码时

## 何时不使用

- 用于琐碎的单行更改或错误修复
- 在使用现有成熟工作流的成熟代码库上工作时
- 用于学习基本Java语法或框架用法时

## 六阶段工作流

### 阶段1：需求定义与边界约束
**目标：** 定义要构建什么、不构建什么以及成功标准。

**核心动作：**
1. **定义项目目标和非目标：**
   - 核心目标：解决什么问题，为谁解决，核心价值
   - MVP功能：仅3-5个核心功能
   - 非目标：明确说明此版本不会做什么
2. **编写标准化需求Prompt：**
   - 包含项目名称、背景、目标
   - 列出具有详细业务逻辑的MVP功能
   - 指定技术约束（版本、框架、数据库）
   - 定义验收标准

**需要避免的常见理性化：**
- “我知道产品管理系统需要什么” → 写下来
- “细节会随着进展而出现” → 提前定义边界
- “我们稍后可以添加功能” → 坚持MVP范围

### 阶段2：架构设计与规范制定
**目标：** 在任何代码生成之前建立技术基础。

**核心动作：**
1. **架构设计与模块拆分：**
   - 让AI输出完整的架构设计
   - 具有明确职责的目录结构
   - 包含索引、约束的数据表设计
   - 核心API接口定义
2. **规范与约束固化：**
   - 创建作为“宪法”的`.cursorrules`/`.agentrules`文件
   - 在`docs/adr/`中创建架构决策记录(ADR)
   - 首先定义公共基础组件（统一返回结果、全局异常处理、工具类）

**需要避免的常见理性化：**
- “Spring Boot有约定” → 仍需要明确的架构
- “AI会遵循最佳实践” → 定义您的最佳实践
- “我们稍后可以重构” → 技术债务会累积

### 阶段3：项目初始化与骨架搭建
**目标：** 在功能开发之前构建和验证项目骨架。

**核心动作：**
1. **项目初始化：**
   - 生成具有正确依赖版本的`pom.xml`
   - 创建带有适当注解的项目启动类
   - 生成包含所有基础配置的`application.yml`
   - 创建所有公共基础组件
   - 生成`.gitignore`
2. **骨架验证：**
   - 运行`mvn clean compile`验证编译
   - 启动项目验证无配置错误
   - 检查目录结构是否匹配架构设计

**需要避免的常见理性化：**
- “让我们立即开始编写功能代码” → 首先验证骨架
- “我们稍后可以修复配置” → 基础错误会导致连锁问题
- “我需要时再添加公共基础组件” → 提前定义它们

### 阶段4：功能模块迭代开发
**目标：** 增量开发功能，每个步骤都进行完整验证。

**标准化功能开发流程：**
1. **功能需求细化：** 为当前模块编写详细提示
2. **实现方案确认：** AI输出方案、涉及的文件、设计思路 - 您确认
3. **代码生成与审查：** AI生成代码，您审查：
   - 代码遵循架构规范
   - 核心业务逻辑匹配需求
   - 参数验证、异常处理、边界条件已覆盖
   - 没有不必要的依赖或硬编码
4. **功能验证：** 编译、启动、测试功能
5. **迭代优化：** 如果不符合预期，向AI提供反馈，迭代
6. **里程碑锁定：** 提交到Git，锁定版本，然后开始下一个模块

**黄金规则：**
- 一次一个功能模块
- “确认方案后再生成代码”
- 在移动到下一个功能之前完成完整验证
- 每个成功功能后提交Git

### 阶段5：测试、调试与问题修复
**目标：** 通过全面测试和系统化调试确保质量。

**核心动作：**
1. **单元测试与集成测试生成：**
   - 单元测试：Service层使用JUnit 5 + Mockito，行覆盖率≥80%
   - 接口测试：Controller层使用Spring Boot Test
   - 测试执行与优化
2. **标准化错误处理流程：**
   - 提供完整的错误上下文（堆栈跟踪、日志、步骤、重现方法）
   - AI首先定位根因，然后生成修复方案
   - 小步修复，避免大规模代码更改
   - 修复后添加测试用例

**需要避免的调试理性化：**
- “只需修复这个错误” → 首先理解根因
- “我太忙了，无法提供完整上下文” → 不完整的上下文浪费更多时间
- “快速修复就足够了” → 快速修复会创建隐藏的技术债务

### 阶段6：文档生成与项目交付
**目标：** 从实际代码生成准确、完整的文档。

**需要生成的文档：**
1. 项目README.md（介绍、功能、技术栈、设置）
2. API文档（Swagger/OpenAPI规范）
3. 数据库表结构文档
4. 架构设计文档
5. 部署与运维文档

**关键原则：** 文档必须匹配实际代码 - AI首先读取所有代码，然后生成文档。

## 核心原则

1. **先规划，后编码：** 在任何代码生成之前进行架构和需求规划
2. **小步快跑，完整验证：** 一次一个功能，在下一个之前完整验证
3. **AI作为熟练工程师，您作为架构师：** 您定义什么，AI实现如何
4. **从代码生成文档：** 从实际实现生成文档，而不是从记忆
5. **Git作为时间机器：** 每个成功阶段后提交，具备回滚能力

## 常见错误（来自RED阶段测试）

| 错误 | 后果 | 正确方法 |
|------|------|----------|
| 跳过需求定义 | 范围蔓延，功能不一致 | 阶段1：定义MVP和非目标 |
| 无架构设计 | 意大利面条代码，难以维护 | 阶段2：在任何代码之前设计 |
| 直接开始功能 | 基础错误，连锁问题 | 阶段3：首先构建和验证骨架 |
| 同时多个功能 | 上下文过载，逻辑混乱 | 一次一个功能（阶段4规则） |
| 测试作为事后想法 | 生产环境质量问题 | 与代码同步生成测试（阶段5） |
| 不完整的错误上下文 | AI无法定位问题，浪费迭代 | 提供完整堆栈跟踪、重现步骤 |
| 最后编写文档 | 文档代码不匹配，信息过时 | 从实际代码生成文档（阶段6） |

## 快速参考

### 阶段顺序
```
需求 → 架构 → 骨架 → 功能（一次一个） → 测试 → 文档
```

### 关键文件
- `.cursorrules`/`.agentrules` - 项目宪法
- `docs/adr/` - 架构决策记录
- `pom.xml` - 依赖管理
- `application.yml` - 配置集中管理

### 验证清单
- [ ] 需求：MVP已定义，非目标明确
- [ ] 架构：设计已批准，.cursorrules已创建
- [ ] 骨架：编译、启动、结构匹配设计
- [ ] 功能：方案已确认、代码已审查、已测试、已提交
- [ ] 测试：已生成、已执行、覆盖率≥80%
- [ ] 文档：从实际代码生成

### 何时迭代 vs 何时继续
- **迭代：** 功能不匹配需求、测试失败、架构被违反
- **继续：** 功能已验证、测试通过、架构保持、已提交

## 实际影响

遵循此工作流的项目显示：
- 后期重构减少60%
- 从一开始测试覆盖率80%+
- 跨模块一致的架构
- 实际匹配代码的文档
- 能够快速上手新开发人员
- 可预测的交付时间表

**记住：** Vibe Coding不是接受AI生成的任何内容。它是关于引导AI生成您需要的内容，并具备您可以依赖的质量。
